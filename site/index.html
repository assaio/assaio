Is it delivering?

Teams pour real money into AI coding tools and cannot answer the one question that matters. Vendor dashboards count tokens and dollars — spend, never output — one silo per tool. assaio reads the session logs already on your machine and weighs what AI produced against the tokens it burned, per project: effectiveness, model fit, context health, adoption. Claude Code, Codex, Gemini CLI, Copilot CLI and Cline in one picture. No account, no upload, no network.

Install · macOS & Linux 
$ brew install assaio/tap/assaio-agent
$ assaio-agent init

About sixty seconds to your own numbers: init detects your tools, shows every directory it will read before reading it, imports, and prints the report. Want to look before importing anything? assaio-agent demo runs the full reports on bundled sample data.

The questions it answers

what you actually want to know

Not "how many tokens did we burn" — every vendor already tells you that. These are the questions a spend decision turns on, and each one is answered from evidence already sitting on your disk.

Within-session churn — removals that undo lines the same session added — beside the tool calls a human declined.

rework · friction

Is the context window being spent on prompt, or on answers?

Cache reuse and what each write bought, conversation depth, and how often a session ran out of context and had to be summarized.

Sessions, active days, and breadth across projects and tools, read as activation → retention → breadth rather than as a headcount.

adoption

Nineteen reads in all, each one file in the codebase, each printing a directional verdict with its caveat rather than a bare score — and each able to be recomputed over just the sessions you labelled a given kind of work, so $/100 lines on bugfixes stops being averaged in with greenfield features.

What it measures, and what it refuses to

the honest scope

assaio measures how much AI is producing, how efficiently, and with how much friction — not how good the result is. That line is deliberate: blurring it would be the easiest way to lie with this tool. The harder problem is that a measurement can be wrong while looking perfectly healthy, so the guards below are part of the product rather than part of the process.

Measured today · offline

Adoption
Tool mix, sessions, active days, breadth across projects, and how much work is delegated to sub-agents.
Effect
AI lines added and removed, read from diff +/- markers and from the body of a file the tool created. The code text itself is never read or stored — only counts.
Efficiency
Lines per token spent, cache reuse and what each write bought, premium-model fit, and cost per 100 lines as an estimate, never the headline.
Friction
Churn that undoes the session's own work, tool calls that failed, and proposals a human declined.

Not measured yet · needs the server stage

  • Survival — whether AI-written code lived on in main after review, rewrites and reverts.
  • Bug impact — whether it caused bugs, only ever against age-matched human code.
  • Quality — maintainability, alongside DORA- and DX-style signals.

These need usage correlated with git and issue history. The local survival command is the first honest step, reading content-free commit observations — counts and a file-category split, never a path, a branch name or a message. Underneath it sits a conformance corpus that defines what an honest session→commit link is before the engine that draws one exists, including scenarios where the evidence genuinely cannot decide: ambiguous has to stay ambiguous, and a human's correction wins.

Principle 01

A silence is never a zero

Your tools do not all record the same things, and a field one of them never writes arrives looking exactly like a measurement of nothing. Read naively, that reports 100% of your sessions were conversational — a sentence about how someone worked, drawn from a column their tool does not keep. Every figure is computed only over the sources that record its field, says how much of your window that reaches, and withholds the verdict rather than certifying a silence.

Principle 02

Every fact carries its provenance

Nothing here is a bare number. Each source publishes what it can actually answer, signal by signal, so signals coverage tells you which of the twenty-two figures your data can carry. Format drift is detected rather than absorbed: per-source canaries compare each import against a baseline of recent runs and warn when a vendor changes a log format under you.

Principle 03

The check whose answer doesn't come from the parser

A test written from a mistaken reading of a log preserves the mistake. So the parsers are held to evidence they did not produce: redacted real traces whose totals were counted by hand, accounting invariants that must hold whatever the numbers are, and metamorphic properties — the same fact written two ways has to produce the same total. That last one is what catches a reader that handles one encoding and silently drops the other, which is what every semantic bug in this project has turned out to be.

Principle 04

One window, one number

The report, the dashboard, a CI gate, a team server and a metric you wrote yourself all read the same window, and a test holds them to the same total. A figure that moved between two screens is a bug, not a rounding difference — and every correction can reach the history already in your store, so a fix repairs the past instead of only the future.

The Assay — an offline dashboard

one self-contained file

assaio-agent dashboard writes a single self-contained HTML file: a verdict faceplate, a bounded top-project drill-down by repository subpath, model and tool mix, and a cost-basis colophon. Light and dark. Project and member names are pseudonymized by default, so it is safe to hand to a teammate or paste into a review — --no-anonymize for real names, which never leave your machine.

Self-contained

No network, no CDN — one file you can open offline or attach to an email. The same posture as this page.

Shareable by default

Pseudonymized project and member names. A team panel appears only on a central store, and it shows engagement per member — output and spend only as a team total, never per person.

Honest on its face

Every cost marked an estimate; unpriced usage flagged, never a fake $0; a "how to read" note per section.

What it reads

five sources · declared depth, not a checkmark

Gemini CLI~/.gemini/tmp/<hash>/chats/*.jsonltokens · cost only

ClineglobalStorage/saoudrizwan.claude-dev · ~/.clinetokens · cost only

"Supports Gemini CLI" is misleading when it means tokens but no edits. Each source publishes its real depth — and it declares that per signal rather than per tier, because "has activity" is one bit over a tool that records changed lines and no edit count, no tool calls and no turns. doctor prints the matrix for the tools found on your machine; signals coverage reads your store and reports each figure as fully, partly or not at all supported. An out-of-tree metric plugin is told the same thing on the wire, so a metric you write yourself can tell a measurement from a silence too.

  • Line activity — lines, edits, rework — is captured in full for Claude Code and Codex; Copilot CLI carries changed lines only; Gemini CLI and Cline contribute cost but no line counts.
  • Copilot CLI totals a session only when it ends, so its records cover a whole session rather than a turn: they are marked ‡ in reports and lower the turn-level coverage every verdict declares.
  • Cline is discovered across VS Code, Insiders, VSCodium and Cursor. Costs come from a vendored snapshot of the LiteLLM price table.
  • The price table is flat per model — long-context premiums aren't modeled yet, so heavy-context sessions under-estimate.
  • A model missing from the table renders — (JSON null, CSV blank, excluded from totals) — never a faked $0. doctor prints every caveat on each run.

More sources — opencode, Aider, Qwen, Roo & Kilo Code — are on the roadmap and buildable out-of-tree today.

Commands

one binary, no runtime deps

initA first run end to end: detects your tools, prints every directory it will read before reading it, imports, reports, and names what to run next. No config needed.
demoFull reports on bundled sample data — the sixty-second first look, no logs needed.
backfillImport local session logs. Incremental: an input already read unchanged is skipped; --full forces a re-parse.
reportToken/cost report. --by day|project|tool|model|entrypoint|member, --format table|json|csv, --compare.
effectivenessAI output against cost — lines, edits, rejections, $/100 lines — per project.
reconcileCheck the estimate against the vendor's own numbers. Point it at a billing or usage export you downloaded — no credential, no network — and it reports the scope mismatch first, names only the causes with evidence behind them, and prints the rest as unexplained. Neither side is adjusted to make them agree.
analyzeRun the metric validators and any metric plugins; print each one's directional read. --task|--outcome|--difficulty recompute every one over just the sessions you labelled that way.
markLabel a session with what the work actually was — task class, outcome, difficulty. --suggest derives them instead of asking: RE2 rules over the branch, skill, agent and entrypoint a session already recorded, yours in config, and nothing at all where a repository has no convention. Category values only, never free text, never synced; the one fact the logs cannot contain.
signalsWhat assaio can report, and what your data supports. describe says what one signal counts and what a zero means; coverage reports each as fully, partly or not at all supported — because "no rework happened" and "this source never recorded rework" are different facts.
survivalDirectional local outcome: how much of a repo's window still lives in HEAD, beside its AI lines, plus what those commits changed by category and how many were reverts. Merge commits are reported apart from the rate, and a file git could not read is counted and named rather than passed over.
dashboardWrite the self-contained offline HTML Assay report; pseudonymized by default.
checkExit non-zero over a token or API-equivalent $ budget — a CI or pre-push gate. Also runs your rule plugins: an error alert, or a rule that could not be evaluated, fails the gate.
digestWhat moved since the last run, in markdown for a weekly thread — and where the comparison itself is weak: overlapping windows, a different window length, a parser that changed between the two runs, a verdict that moved on thin confidence.
explainThe long-form page for a metric — what it measures, how to read it, what to do, and its limits. Needs no store.
statuslineOne ambient line for your status bar: today's tokens, AI lines, cost basis and data age. Read-only, never fails loudly.
serve · syncSelf-hosted team server and the push to it — pseudonymous by default, on infrastructure you control.
doctor · statusDetected tools, resolved log roots, store size, the per-source depth matrix, and format-drift canaries. doctor --strict exits non-zero on suspected drift — for cron.
docsEverything this binary can enumerate about itself — signals, sources, validators, commands, settings, the plugin protocol — as JSON or as a page. The published reference is generated from it, and a check fails the build when this site and the binary disagree.
plugins · metricslist / verify out-of-tree exec parser, metric and rule plugins — nothing stored.
config · clear · compactPrint the effective config; delete stored data with an explicit scope and --yes; return freed pages to the filesystem.

Cost honesty & the team server

estimate, not invoice

Every $ is an estimate

Priced at public pay-as-you-go rates — not your bill. Token counts are computed server-side and unobservable to an offline client.

Check it against the invoice

reconcile compares that estimate with a vendor export you downloaded yourself, offline. A delta it cannot explain is printed as unexplained — the number is never quietly moved to close the gap.

Declare your real basis

On a subscription or a negotiated rate? Set pricing — an effective $/token or a monthly plan cost — and reports show a truer figure. subscription-fit then reads whether the plan pays off.

Budget gate

check --max-tokens N exits non-zero over budget — plan-independent by default, for CI or a pre-push hook.

Team server, self-hosted

serve pools usage that teammates sync to it and serves one aggregated, pseudonymized dashboard. You host it, on infrastructure you control.

Adapt it to your organization

built to extend

One tool = one package; one metric = one file. Extend assaio without forking — exec plugins are standalone executables in any language, declared in your config and speaking a small stdout protocol, so they survive core refactors. Three protocols: data sources, metrics, and rules that gate CI.

Data source · any language

An out-of-tree parser — Python, Rust, shell — for a tool assaio doesn't read yet. plugins verify checks conformance, and a field the protocol doesn't define is a named error rather than a silent zero. Or add one in-tree via PR.

Metric plugin · any language

An analyzer that reads the same prepared data every built-in metric reads and returns one result — it renders in analyze and on the dashboard, no rebuild.

Rule plugin · any language

A gate of your own: it reads this window's verdicts — never usage rows, never project names — and raises alerts that can fail check in CI.

Query the store

The SQLite schema is documented — query it with sqlite3 or any client, or pipe report --format json|csv into your own BI.

Privacy first — and what it will never do

refusals

Local analysis never touches the network — no account, no telemetry, no upload. assaio reads token and line counts, never your prompts or your code. The store holds a project basename, never a full path.

  • No "estimated time saved." The logs contain no counterfactual, so any such number is invented.
  • No leaderboards. Nothing is ranked per named individual — aggregate and pseudonymized by default, and the team panel shows engagement rather than output per person.
  • No silent precision. Directional signals say so; an unpriced model renders a blank, never a fake $0.
  • No per-person analytics outside a deliberate, governed team-mode opt-in.

Where this is going

direction, not commitment

The order the work is meant to happen in — no dates, no guarantees, and any item can be reshaped or dropped when a bug report or a pull request makes the case — lives in ROADMAP.md, next to the reasoning behind the ordering and the conditions v1.0 has to meet. It used to be copied onto this page as eight cards, which meant a section that had to be re-read at every tag and could describe things that do not exist. A promise is worth stating once, in the place it cannot fall behind.

What you can install today is the latest release; the feature inventory says what that gives you, and the reference is generated from the binary itself — every signal, source, validator, command and setting it actually has.

Why "assaio"?

assay + io

An assay is the metallurgist's test: what a piece of ore is actually worth.

Ore can glitter and still be worthless. That is precisely the question engineering organizations face with AI coding tools — plenty of glitter, tokens burned and dashboards full of activity, and very little honest measurement of what any of it is worth.

assaio is built to be that test. It measures the real value in the ore, and it would rather show you an honest blank than a precise-looking number that is wrong. The metaphor sets the ethics too: an assay examines the metal, never the miner. assaio measures value, not people.
